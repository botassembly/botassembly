# CLI command and output matrix

## Common contract

This page describes current commands and explicitly marked drafts. The [current plan](../plan.md) owns priority.

The first word after `bot` is a noun or `capabilities`. The second word is an action. `--help` remains the only global action that can appear without a noun. Every command accepts `--home` through one common parser when the command reads a Bot home. Resolution uses explicit `--home`, then `BOT_HOME`, then the platform default. `home show` is the explicit-only exception because it discloses which installation owns the selected directory. It requires `--home` and does not consult either ambient source.

Finite human answers are Markdown. Finite program answers use `--json` or `-j` and contain one object with `schemaVersion`, `kind`, and `data`. Lists also contain `page` and `summary`. Streaming program answers use JSON Lines and put one complete object with a schema version and cursor on each line. Exact bytes require `--raw`. JSON, follow, and raw modes are mutually exclusive unless the command matrix says otherwise.

Standard output carries only the requested answer. Diagnostics, progress, and human notices use standard error. A successful JSON command puts warnings, truncation facts, and page facts in its result instead of writing prose to standard error. A structured failure uses the same human or JSON rendering mode as the request and carries `code`, `operation`, `cause`, and the identities known at the failure site. A raw failure before copying starts writes no standard-output bytes. A read, standard-output delivery, or descriptor-close failure after copying starts may leave exact bytes already written. It writes one bounded human diagnostic to standard error and exits with the common code. A caller can request structured failure metadata only when that command has a non-raw JSON form. Exit 0 means completion, including an empty valid list. Exit 1 means a valid predicate was false or a requested state was not reached. Exit 2 means malformed invocation or input. Exit 3 means a revision or precondition conflicts with current state. Exit 4 means a temporary dependency failure. Exit 5 means an internal or integrity failure. A run result preserves its recorded exit.

Finite lists default to a bounded page. `--limit` has a documented maximum. `--after` is an opaque keyset cursor with encoded and decoded byte limits. Repeatable filters have value and byte limits that keep every emitted cursor safe to reuse as one command-line argument. `--fields` selects supported fields after authorization and validation. `--count` returns an exact count without rows, retains no row collection, and never forces unrelated detail reads merely to satisfy it. Filters use typed repeatable flags and run before rendering. Human tables render retained text as bounded inert Markdown. Warnings are bounded and report the exact omitted count.

## Result details

`bot.run.result` always carries `run`, `exit`, `cause`, `startedAt`, and `complete`. It carries `endedAt`, `reason`, `terminalStage`, `donor`, `correlation`, and `output` only when those facts exist. A resumed result always carries a durable carried-stage count. It includes the full ordered identities when the result bound permits and otherwise reports that it omitted them. A completed record supplies `endedAt`; an incomplete record does not invent one. An output descriptor carries its record-relative path, extension, byte count, and SHA-256. A small complete payload may also carry exact UTF-8 text or base64 bytes when the whole result stays within its published document bound. Larger content remains available through the output artifact command. Callers never need to parse the run record to learn the terminal result. Usage remains a separate reading of retained turn events. `--id-file` writes the run id atomically after the run directory and `run_start` exist, so a local supervisor can inspect live work before the terminal result arrives.

`--correlation` is opaque caller metadata. Bot records the supplied value with the run and returns it in structured readings. Reusing a correlation identifier starts another run. The identifier creates no replay behavior.

One initialized home stores its installation identity in a private atomic `installation.json` record. `home show` requires explicit `--home`; it does not use `BOT_HOME` or the platform default. Its capability option descriptor marks `--home` with `required: true`. An absent show returns `initialized: false` without mutation when that requested result fits. A first start or resume creates a missing identity before it creates a run. Concurrent first runs use the one stored identity. Invalid, insecure, or result-infeasible state fails without repair. Moving the home preserves the identity only when the reported destination also passes result feasibility. A copy preserves it only when the copy preserves bytes, ownership, modes, and result feasibility. Every new `run_start` records `installation_id`, and structured start and resume results return that same successfully written value as `installationId`. The stored record, finite result envelopes, run record, and capability result remain at version 1 under the pre-release change-in-place policy. Bot provides no identity reset.

`capabilities -j` names the package version, Git source state and digest, source-tree hash, every implemented new command, mode, accepted option, bound, contract version, and `never`, `conditional`, or `requested` network behavior. It also names mutation and home behavior. Source identity uses the same resolver as `run_start`. Its sequential source observation is not atomic and has no separate inventory quota. Planned commands enter the result only when their executable behavior lands. Compiled metadata remains shared by parsing and help. Help, dispatch, and capability discovery cannot drift into separate command inventories. The bounded result needs no filter in the first surface.
