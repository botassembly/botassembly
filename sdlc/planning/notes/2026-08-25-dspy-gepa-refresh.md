## 1. What shipped in DSPy since 2026-07-16

Two releases: 3.3.0 (59e8c40f8, 2026-08-03) and 3.3.1 (4ed377ee9, 2026-08-21). The homepage blurb for 3.3.1 is "PythonInterpreter improvements, faster GEPA, and MCP v2 compatibility" (19b1ca6ab, `docs/hooks/fetch_stats.py`).

### dspy.Flex — program code becomes the optimization candidate (the big one)

Commit e4e97aae2 ("feat(dspy.Flex) + GEPA extension", 3.3.0) adds `dspy.Flex`: a module whose tunable parameter is not a prompt but the **source code of a whole `dspy.Module` subclass**, held as a string (`module_src`). Observed in `dspy/predict/flex/flex.py` and `docs/docs/diving-deeper/flex.md`:

- The baseline is the simplest thing that runs — one `dspy.Predict` over the signature, or `dspy.RLM` when tools are given (`_baseline_src()` in `flex.py`).
- GEPA discovers `Flex` submodules by type and splits its work: each Flex is a "code component" evolved by a dedicated code proposer; ordinary predictors stay "instruction components" on the usual proposer (`dspy/teleprompt/gepa/gepa_flex_utils.py`, flex.md design decision 3). The code proposer reflects on whole-program I/O plus metric feedback, not per-predictor traces, because next candidate's predictors may not exist (decision 4).
- Generated code never runs in the host process — always a Deno/Pyodide sandbox with a narrow `dspy` shim (`dspy/predict/flex/_sandbox_shim.py`); predictor calls and tool calls bridge back to the host, which makes the real LM calls (decision 7).
- A candidate that fails to parse scores the whole batch at the failure score; code that crashes on some inputs fails per example, by index, keeping GEPA's per-instance bookkeeping aligned. "Robust to the reflection model's mistakes by construction" (decision 6).
- Saved state is just `{"module_src", "lm"}` — the code is the state, internal predictors are derived (decision 9). Marked `@experimental(version="3.3.0")`.

Alongside this, `CodeAct` and `ProgramOfThought` were deprecated (99bb44bf4), with flex.md positioned as the replacement direction.

**Interpretation.** This is Drew Breunig's "crystallization" made into a first-class mechanism: the optimizer literally rewrites LM steps into plain Python when the metric rewards it, moving work out of the model entirely. The guidance file the code proposer sees says "Define a predictor ONLY for a step that genuinely needs a language model. If the task needs no LM at all, define no predictors" (`dspy/predict/flex/primitives_doc.py`, wording visible in the 573cfe707 diff). That is the LM→code direction stated as policy inside the optimizer's own prompt.

### GEPA in DSPy: faster, multi-objective, engine 0.1.4

- aa9d2d053 upgrades the vendored engine dependency to gepa 0.1.4 and allows an unset reflection cost budget; 822f39319 parallelizes candidate evaluation with thread distribution.
- 638e155cf adds **objective-aware optimization**: a metric may return named `objective_scores` alongside the scalar; `frontier_type` becomes `"instance"` (default) / `"objective"` / `"hybrid"` / `"cartesian"`. Critically, per `docs/docs/api/optimizers/GEPA/overview.md` in that diff: "The scalar score still gates acceptance and determines the final candidate; objectives only affect parent and merge selection."
- 80553206b exposes optimizer compile events through the callback system; b11cfe874 exposes interpreter lifecycle events.

### ReActV2 and the caching story

429af9125 adds `docs/docs/diving-deeper/react.md` documenting the transition: `ReActV2` becomes the implementation behind `dspy.ReAct` in 3.5. The differences that matter (observed in that doc's comparison table): structured `dspy.History` events instead of a flat trajectory dict; prior turns **replayed as separate messages so the stable prefix stays reusable by provider prompt caching** (old ReAct re-formatted the whole growing trajectory into one input field every call, busting the cache); multiple tool calls per model turn via `dspy.ToolCalls`; and `submit` carries final typed outputs directly, deleting the separate extraction LM call. 573cfe707 then steers Flex's optimizer-authored code toward `ReActV2`. There is no new program-level caching machinery in this window (the cache commits, e.g. c53e24904, are test infrastructure); the caching story is prompt-shape design, not a cache layer.

### Smaller but relevant

- Adapters: nested XML data support (33aaa19e0); correct behavior for optional/default output fields (ba8a64958); default timeouts on `Image.from_url`/`Audio.from_url` (564d24cd8).
- MCP v2 SDK support without changing result semantics (32bcd36ce) plus opt-in structured results for MCP tools (ca0a088bd).
- A long run of `PythonInterpreter` sandbox hardening: isolated Deno cache (ab8a7658d), rejected colliding file mounts (072c72164), desync on unhandled sandbox rejections (6334c2ba5), robust request handling (80b118e52).

Nothing in this window is about cheaper-model *routing* as such — no auto-tiering shipped. **Interpretation:** DSPy's cost story right now is (a) crystallize steps into code via Flex, (b) make prompts cache-friendly via ReActV2, (c) parallelize GEPA; model-tier assignment remains the user's job, which matches the notes' stance that profiles/tier are our lever, not the engine's.

## 2. What changed in the standalone gepa repo

Since our 2026-07-16 local head (e747ada0), roughly 25 substantive commits:

- **ReflectionLM protocol + batch parallel proposals** (8b0ce6cd, release 0.1.4): `reflect()` returns `(proposal, next_lm)`; parallelism moved to `adapter.batch_evaluate()` and the LM while the engine stays sequential; sampling strategies (`SingleMutationSampling` default, `SameParentSampling`, `IndependentSampling`, `PxNSampling`) and selection strategies (`AllImprovements` default, `BestImprovement`, `TopKImprovements`). Defaults reproduce the old single-proposal behavior.
- **ComBEE** (bb1c9473 and the ~15 fix commits after it): a ReflectionLM implementation that aggregates parallel "scan" reflections in two waves across all proposals — a committee-style reflection.
- **Engine-pluggable `optimize_anything`** (6d897c1e, ~10k lines): `src/gepa/oa/` now holds interchangeable backends — `engines/gepa.py`, `engines/autoresearch.py`, `engines/best_of_n.py`, `engines/meta_harness.py` — plus `eval_server.py`, `sandbox.py` (sandbox on by default per 430dc3e3), and `proposers/claude_code_agent.py`. The repo's own skill (`.claude/skills/gepa-optimize-anything/SKILL.md`) frames it plainly: write the evaluator once, switch optimizer backends with one argument; the backend sees only score + feedback text, never the metric internals.
- **Agent-readable run state** (in the 6d897c1e series): with a `run_dir`, GEPA writes `gepa_state.json` — every candidate with parent lineage and cost, per-candidate per-datapoint scores, Pareto frontier detail, the full iteration log with side_info, the evaluation cache, **and a `rejected_proposals` section explaining why proposals were rejected** — explicitly "so autonomous agents (e.g. Claude Code) can see WHY proposals were accepted or rejected" (commit body).
- **The Claude Code agent proposer** (`src/gepa/oa/proposers/claude_code_agent.py`): plugs in via `custom_candidate_proposer` (which gets the structured reflective dataset; the `reflection_lm` hook is text-in/text-out and does not). It writes candidate, reflective dataset, and components-to-update as files, launches `claude --print` over that directory, lets the agent browse `iterations/`, `pareto/`, `history.md`, reads one file back per component, and falls back to the original text on a missing file so acceptance simply rejects the no-op.
- **A serious cache bug fixed** (ef525a44): the evaluation cache was keyed by `(candidate, example id)` where example id was *position in the loader*, so valset lookups could be answered by the trainset rollout at the same index — "affected candidates got a full valset score vector while never running some of those examples, and the fabricated per-instance scores fed the Pareto front and parent selection." Fixed by namespacing reads/writes with a split.
- **Reflective trace slimming** (b265bf9c): the reflective context now keeps the *last call per distinct predictor* rather than everything, after last-entry-only collapsed ReAct repeats but dropped other modules in a pipeline.
- Result unification on a single `GEPAResult` return for optimize_anything (65130973); trace-aware batch evaluation fixed for accepted candidates (a477710b).

## 3. skilled-proposer — first review

What it is, observed (`~/foss/skilled-proposer/src/skilled_proposer/`): a single class `SkilledProposer` implementing GEPA's `ProposalFn` protocol `(candidate, reflective_dataset, components_to_update) -> dict[str, str]` (`proposer.py`), so it drops into `dspy.GEPA(instruction_proposer=...)` or standalone gepa. It replaces only the meta-prompt and its surroundings; the engine, gate, and search are untouched.

The mechanism, piece by piece:

- **The meta-prompt is a three-step procedure with an explicit anti-overfitting contract** (`signatures.py`, `ProposeGeneralizableInstruction` docstring): (1) infer the task, because "the assistant will see only your instruction — never these examples"; (2) diagnose each failure and find "the general rule … that would have prevented the failure — one that helps on any input where the same mistake could recur, not just on this example"; (3) write the replacement, preferring "a few high-leverage rules over exhaustive case lists". Then the principle: "The specific entities, quantities, dates, and answers in these examples belong to the examples, not the task — a description of correct output like 'a single ISO-8601 date' transfers; the date itself does not." The README explains the motivation: GEPA's stock proposer tells the reflection model to include "niche and domain specific factual information" from traces, which can copy training answers into the prompt.
- **Skills as reference material for the reflection model** (`skill.py`, README): each entry — a SKILL.md directory, a markdown file, an inline string — becomes a `<skill>` block in the proposal prompt. Deliberately, loading a skill directory reads *only* SKILL.md, never subfolders: the proposer runs as a plain LM call with no filesystem, many times per run, and "what the reflection model should see is also known before the run starts" — so the developer hand-picks the extra files (e.g. the student model's vendor guide) and passes them explicitly.
- **The shipped skill is a per-model prompting library** (`skills/prompt-engineering/`): SKILL.md defines a 10-step eval-driven loop (define → run → categorize failures → select a technique → *consult the student model's vendor-specific file* → re-run → log), and `models/` holds one guide per vendor — anthropic.md, openai.md, google.md, deepseek.md, meta.md, qwen.md, xai.md — with concrete per-model quirks (effort levels, thinking behavior, migration notes).
- **A length budget with an enforcement ladder** (`proposer.py`, `_enforce_length`): prompt constraint first, then one LM compression pass (`CompressInstruction`), then hard truncation — with a binary search for the largest word prefix fitting a token budget.
- **Survivability defaults**: `on_error="keep"` logs a failed proposal and keeps the current instruction so one flaky call doesn't kill a long run; `max_examples` caps reflective examples per component to bound the meta-prompt.

Limits observed: v0.1 is text-only (rich values stringified, README "Limits"); proposals are made per-component sequentially in a plain loop (`__call__`), so it predates gepa 0.1.4's batched-proposal machinery.

**What botassembly should steal (interpretation):**

1. **The meta-prompt itself, nearly verbatim.** The generalize-don't-memorize contract is exactly the failure the campaign measured (the optimizer buying format instead of judgment), attacked at the proposal stage instead of only at the accept gate. Cheap defense-in-depth: gate catches Goodhart candidates, proposer stops manufacturing them.
2. **Model guides as proposer context = the mechanism for per-profile optimization.** The notes' rule — optimize each stage's wording against the model that stage runs on — needs the proposer to *know* the target model. skilled-proposer's answer: pass the vendor guide for the student model as a skill block. For botassembly: when optimizing stage N under profile P, inject the model guide for P's model at stage N into the reflection prompt. This turns "profiles" from a routing table into optimizer knowledge.
3. **Developer-curated proposer context, no filesystem browsing.** The decision to resolve skill content before the run, not let the proposer wander, matches botassembly's sealed-inputs instinct and keeps proposal cost bounded.
4. **The length budget ladder and `on_error="keep"`** — small, directly reusable robustness patterns for overlay proposals (an overlay that balloons is its own failure mode).

**What to avoid:** nothing structural. It is ~350 lines with no dependency beyond dspy; the pattern transfers even if the code doesn't. Don't inherit its per-component sequential loop if the bench parallelizes; don't inherit its text-only rendering assumption if run records carry structured artifacts.

## 4. Synthesis — what botassembly harvests, conceptually

**The decided design is validated, twice, and in one place extended.**

- **Overlay-only via the candidate dict — confirmed and strengthened.** GEPA's candidate remains `dict[name → text]` and everything new (ReflectionLM protocol, batched proposals, ComBEE, skilled-proposer) keeps that contract. The overlays-only rule stays enforced by what the dict contains. Flex is the one place DSPy widened the candidate to *code* — and botassembly's counterpart of "code" (scripts, schemas, gates) is frozen under optimization by Ian's ruling. Interpretation: that is a conscious divergence, not an oversight, and it should be recorded as one. If a crystallization step ever exists — the optimizer proposing "this LM stage could be a deterministic check" — it is a *new assembly version*, invalidating prior optimization, gated by humans; Flex shows what the search looks like when you allow it, including the essential safety pattern that **a broken candidate scores as a failure, never crashes the search** (flex.md decision 6). Steal that pattern for the accept gate regardless: a malformed overlay costs one search step, not a run.
- **E15 (GEPA vs our introspector) now has a middle path — and upstream built our side of it.** gepa's `claude_code_agent.py` proposer is diagnose-then-propose with filesystem access to run history, plans, and the Pareto tree — structurally Ian's introspector loop, packaged as a GEPA proposer. Interpretation: E15 need not be engine-vs-engine; the cleaner experiment is GEPA's engine with three proposers — stock, skilled-proposer-style, and agent-with-records — under the same gate. The engine (Pareto tracking, budgets, resume, state) is commodity; the proposer is where the ideas differ.
- **Rejections-remembered exists upstream now.** `gepa_state.json` records rejected proposals with the eval-before/eval-after evidence for why, written explicitly for agent consumption (6d897c1e series). Harvest the shape of that file when designing `optimizer/state/` rather than inventing a format; it is also exactly what a dashboard page over an optimization run wants to render.
- **Objective-aware frontier matches the gate/selection split.** DSPy's rule — scalar gates acceptance and picks the final candidate, named objectives only steer parent/merge selection (638e155cf) — is the same separation as botassembly's "deterministic checks gate, judge comparison gates, everything else is diagnostic." Interpretation: botassembly's per-check results are natural `objective_scores`; feeding them to the engine improves search direction without ever touching the accept gate. Cheap to adopt, changes no decided rule.
- **A cautionary tale for the bench's cache:** gepa's valset/trainset cache collision (ef525a44) came from identifying examples by *position*. Botassembly's sealed, content-addressed run records already avoid this by construction — keep it that way, and key any eval-reuse by case content hash plus split, never index.
- **Reflective context wants curation, not volume.** b265bf9c (keep the last call per distinct predictor) and skilled-proposer's `max_examples` both push the same way: the reflection prompt should get the *decisive* slice of a run record — the failing stage's I/O and the check's written "why" — not the transcript. This is more support for "every check writes its why" being the fuel, and a design input for how the bench serializes a run for the proposer.
- **Per-model optimization is where the field landed.** DSPy still has no auto-tiering; what shipped instead is (a) code crystallization via Flex, (b) cache-friendly prompt shape via ReActV2's stable message prefix, and (c) proposer-side model knowledge via skilled-proposer's vendor guides. Interpretation: that triangulates the notes' position — tier assignment is our lever (profiles), wording-per-model is the proposer's job (model guides in context), and the long-run cost curve comes from moving stages off the LM entirely (crystallization, which for botassembly means promoting LM checks to deterministic ones, human-gated). The ReActV2 lesson applies to bot's own stage prompts today: keep the stable material in a stable prefix and append the changing material, so provider prompt caching pays.
- **Cost/wall-clock (open item 4) has upstream relief:** parallel candidate evaluation in dspy.GEPA (822f39319) and batched multi-proposal sampling in gepa 0.1.4 (8b0ce6cd) both attack optimizer wall-clock and per-run call counts; the sampling/selection strategy names are worth adopting as vocabulary even in our own loop.

**One-line verdict:** nothing in six weeks of DSPy/GEPA contradicts the decided design; the overlay-dict, gate-above-engine, feedback-as-fuel choices all got *more* canonical upstream. The genuinely new inputs are skilled-proposer's model-guide-in-the-proposer pattern (adopt for profiles), `gepa_state.json` (adopt the shape for rejection memory), objective_scores (adopt for check-level steering), and Flex (name the divergence: we froze the code surface on purpose, and crystallization, when it comes, is a versioning event, not an optimization event).
