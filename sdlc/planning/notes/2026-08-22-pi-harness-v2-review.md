# Pi harness v2 — review of the durable AgentHarness work

Moved from Ian's notes vault on 2026-09-24. Written 2026-08-22; nothing was rechecked on the move.

A deep read of the `harness-v2/j4` branch of the pi repo and of everything harness-related on `main`, researched 2026-08-22.

## TL;DR

Pi is building a new execution engine called the **AgentHarness**: a durable, crash-safe runtime for agent conversations, with multiple parallel "lanes" per session (think a Slack channel where each thread is a lane), an explicit-state design where recovery after a crash is a handful of register reads rather than log replay, deterministic step-by-step testability, and a typed telemetry system. It has been landing on main in slices since early May 2026. The design document went through three drafts in the first half of August (v2 on the branch, then an explicit-state redesign, now consolidated as harness-v3 in `packages/agent/docs/harness.md`), including two AI-assisted cold-read audit rounds that found 17 spec defects, all since fixed. The branch `harness-v2/j4` is one slice of this effort — backward compatibility: teaching the new session store to read old coding-agent v3 JSONL files. It was written against the v2 design, which main has since superseded, so the branch is both valuable (the compat rules it encodes survived into the v3 spec as Appendix B) and partly stale (its code types will be rebuilt). The interactive pi you run today still uses the old coding-agent runtime; the harness is the platform underneath the future server-side, multi-session, multi-lane pi.

## The v2 design (what the branch doc describes)

The branch doc "Durable AgentHarness design" is organized in three parts: Concepts, How execution is recorded, API and implementation. Its core model:

- A **session** holds four kinds of state: the conversation **tree** (immutable entries with parent links — messages, model/thinking/tool-activation changes, compaction summaries, branch summaries, custom entries), **lanes** (named cursors with a leaf position), **lane operation logs** (append-only chronological record sequences per lane — the durability mechanism), and **global facts** (session name, entry labels, latest-write-wins with append-only history). All writes share one monotonic sequence number.
- **Lanes** run in parallel inside one harness; each lane runs at most one operation at a time. The doc's analogy is a git branch checked out in its own worktree. A Slack channel is a session; each thread is a lane. Interactive pi would use one lane and hide the concept; extensions get the full API; a subagent tool runs on a second lane of its parent's session.
- **Operations** are the unit of durable work: a run (an accepted prompt through all automatic continuations), a compaction, or a navigation. Acceptance is durable — after a crash an accepted operation is either completed by recovery or explicitly closed.
- **Records** are how durability works in v2: one flat chronological record sequence per lane (operation started, step attempted, tool started, message queued, operation finished). "Records exist so that a new process can continue a lane's work after a crash. Nothing reads them during normal execution." Recovery replays/reduces the record log to figure out where the lane was.
- **The effects boundary** is the key testing idea: every effect — durable write, provider request, tool execution, hook, timer — crosses one injected boundary. In `drive: "manual"` mode the harness parks before each effect and a test drives it call by call: stop at any boundary, inject input, or close and reopen to simulate a crash. Production and tests run the same procedures; only the drive mode differs.
- **The lane mutation line** closes the check-then-act races: every state-dependent decision commits inside one job on a per-lane FIFO promise chain, so two concurrent operations on a lane have exactly two possible histories, both defined.
- **Events vs hooks**: events observe execution and cannot change it; hooks intercept and can (before_tool can block a bash call, and fails closed — a throwing policy hook blocks the tool).
- **Two input mechanisms**: queues carry conversational intent (steer, followUp, nextRun) and die on abort; deferred writes carry facts and config changes and survive abort. Both are durable at acceptance — accepted input is never lost.
- **Deferred provider requests**: a `background: true`-style request returns a persisted handle; recovery fetches the result instead of paying for a new request. `stopReason: "deferred"` with a `DeferredHandle` is a first-class message state.
- **Forks**: one copy primitive, entries only — no records, no cost ledger. A subagent's child session id is derived deterministically from (parentSessionId, toolCallId) so a safe replay reattaches to the same child instead of spawning a twin.
- **Compat policy** (the reason j4 exists): old coding-agent v3 JSONL sessions must open and restore idle. That is the only backward-compatibility requirement; everything else in the harness internals may break, with no migrations or schema versioning for anything else.

## The v3 design (what main's consolidated spec describes)

The consolidated `harness.md` keeps the lanes/operations/hooks/events/deferred/forks ideas but restructures the durability model around one big change: **explicit state instead of records**. The core is stated as "the three stores" and a "durable program counter":

- **Three stores, one invariant.** Everything durable is exactly one of: **entries** (the conversation tree, write-once append-only), **registers** (mutable namespaced typed cells — current state, overwrite or delete), or the **usage ledger** (append-only cost rows). "Every payload is in an entry, a register, or the ledger; there is no third place." Per-backend projections (branch index, full-text search, stats) are rebuildable and carry no authority.
- **The durable program counter.** After every step the harness overwrites one register — `op.state/{operationId}` — with the *complete* current state of the operation. Recovery does not replay a journal or infer position from what is missing; it reads that register and switches on it. The state is *total* — it never depends on a previous state. When the operation ends, the terminal transaction deletes its registers: a finished session holds exactly the conversation, the ledger, and a handful of lane and fact registers. "There is no dead state to collect."
- **The effect sandwich.** Provider requests and real tool calls are wrapped in two commits: an **intent** commit ("about to do X; its output will use ids R and U", ids minted before anything is sent), then the effect (the only non-durable part — "the uncertain window"), then a **settlement** commit (output + usage + next state). Kill the process anywhere and the registers say exactly which sentence was last committed.
- Worked examples walk a Slack-thread prompt and a crash mid-tool through their exact transaction sequences, including the replay policy: a tool that declared `replay: "never"` (a deletion) gets a synthetic "interrupted" result after a crash so the conversation stays coherent and nothing runs twice; a `replay: "safe"` tool (a read) is re-executed with the persisted arguments.
- **Recovery is a read**: five register point-lookups per lane, then exact-id dereference. "No reducer exists to have a bug."
- v2's operation-log records and append-only global facts are gone; registers replace both, and the absence of write history is now an explicit non-goal ("Durable write history. Registers hold only current values"). Cost history is what the new usage ledger is for.
- **Schema evolution** gets its own part (Part 7): a session-level `storageVersion`, chained migrate-on-open migrations under the writer lease, and the rule that **migrations are total** — every state-machine change ships the mapping that carries every reachable old `op.state` into a well-defined new one, in the same change. The design argument is that because the mutable surface is a few dozen current registers (open operations usually zero), this is tractable — whereas years of entries can never be rewritten and must stay read-compatible forever.
- **Build order** (Part 8): 16 slices. Slice 1 deletes `packages/agent/src/harness/**` and its tests outright and lands the complete v3 type surface. Then two tracks that cannot block each other: Track S (JSONL format 4, SQLite, search, dev TUI — parallelizable) and Track R (runtime: minimal no-tool run, recovery/retry, tools, inbox/config, abort/close/failure drain, deferred redemption, compaction, overflow, navigation, migrations, surface completion — strictly sequential, built entirely against the Memory backend). Each slice has named focused tests and "stop and send it for review if implementation exposes a design contradiction" as its acceptance rule.
- **Invariants and tests** (Part 9): 21 numbered invariants, a 12-row race catalog where each race has exactly two durable histories and both orders must be tested in manual drive, and three test tiers — state/resume (construct every state, close, reopen, assert next action), writer conformance (an instrumented storage decorator around `commit()` as the oracle, asserting exact write order), and deterministic interleavings. Drive equivalence: the same scenario in automatic and manual drive must produce byte-identical durable state.
- The appendices carry the glossary, the coding-agent v3-format compatibility rules (Appendix B — the j4 subject matter, restated for the v3 model), and three open questions.

## How SQLite is thought about

The v3 spec's SQLite section is one of the sharpest parts of the document, and it leans on SQLite's constraints rather than fighting them:

- **One database file per session.** The file *is* the session, exactly as a JSONL file is. Corruption is confined to one session, deletion is unlinking a file, and "SQLite's one-writer-per-file rule coincides with the design's one-writer-per-session rule by construction." Forks and the precise rewrite become file operations (`VACUUM INTO` or row copy over one read snapshot, then atomic swap).
- **Every transaction opens with `BEGIN IMMEDIATE`**, and the spec explains why in detail: a deferred `BEGIN` that reads before it writes takes a read snapshot and must later upgrade to the write lock; if another writer committed in between, SQLite fails the upgrade and `busy_timeout` cannot rescue it, because no amount of waiting refreshes a stale snapshot. Since every commit allocates sequence numbers (reading `next_seq` then writing it), every transaction reads-then-writes — so deferred `BEGIN` is never correct here. There is a test tier asserting every transaction opens `BEGIN IMMEDIATE`.
- **`writer_lease` enforces the single-writer rule with fencing**: WAL happily lets two processes alternate writes to one file, which is exactly the interleaving the design forbids. The lease expires with an (owner_id, fence) pair so a stale owner cannot release the replacement that succeeded it. Memory and JSONL have no equivalent and rely on process ownership — "a JSONL session opened twice is corrupt and undetected."
- **The private branch index** is a per-backend projection, not registers: `branch_entries` + `branch_meta` tables with ordered covering indexes, and a load-bearing `CROSS JOIN` in the scan query that forces `branch_entries` to be the outer loop — left to itself the planner may drive from `entries`, scan the table, and sort through a temporary b-tree. The test asserts the exact `EXPLAIN QUERY PLAN` shape ("Any plan containing `USE TEMP B-TREE FOR ORDER BY` or a scan of `entries` is a regression").
- **JSONL is "the replay recipe" for the Memory maps**, one physical line per commit, array lines for transactions, with a torn final line discarded whole and truncated before new writes are admitted — that is what makes "no crash prefix inside a transaction" true. Because every register `set` appends a line that is dead the moment the terminal delete lands, the file grows with write history; snapshot compaction rewrites it as header + current entries + current registers + usage rows via temp-file-and-atomic-rename, keeping original seq values so gaps (which are legal) need no renumbering. Logical deletion is immediate; physical deletion is deferred to compaction — the spec calls out that a deployment needing prompt physical removal of sensitive cancelled content compacts eagerly at terminal boundaries.

## How telemetry is thought about

Both the v2 and v3 docs treat telemetry as a first-class design concern, with v3 inheriting and tightening the v2 rules:

- **No ambient context, ever.** Core code does not use `AsyncLocalStorage`, global current-span state, or runtime-specific context APIs, because pi runs in Node, Bun, browsers, and workers — no runtime's ambient-context mechanism can be the core abstraction. Parent spans are passed explicitly. An adapter may use ambient context internally (an OpenTelemetry adapter may activate its native child context so HTTP auto-instrumentation attaches), but pi always passes the parent.
- **Typed schemas as code.** The generic contract, schema machinery, no-op, and in-memory reference implementation live in `packages/telemetry` (exported as `@earendil-works/pi-telemetry`); the agent package owns the domain schemas (`AI_TELEMETRY_SCHEMA`, `HARNESS_TELEMETRY_SCHEMA`) in `packages/agent/src/harness/telemetry.ts`. The generated [`telemetry-schema.md`](https://github.com/earendil-works/pi/blob/main/packages/agent/docs/telemetry-schema.md) enumerates every span (`pi.harness.run | compaction | navigation | checkpoint | turn | step | tool | hook | sleep | event_handler`, `pi.session.write`, `pi.ai.request`) with required start attributes (operation, provider, model, api, streaming, deferred) and optional end enrichment (response model/id, stop reason, HTTP status, token and cost usage, time-to-first-chunk, error class).
- **Pi ships no exporter** and requires no backend-specific implementation; `InMemoryTelemetryContext` is the deterministic backend-neutral reference. Adapters bridge spans into OTel, Sentry, or logs.
- **The v3 rule on content**: telemetry attributes may contain declared ids, names, counts, durations, statuses, and usage — never prompts, completions, tool arguments/results, file contents, provider payloads, headers, handles, or credentials. Events and hooks may contain such content; telemetry may not. Synthetic settlements and blocked tools emit no provider/tool span, and every storage transaction emits one `pi.session.write` span carrying item counts and kinds plus first/last committed sequence.

## Search (how it fits)

Search in the v3 design is a **standalone service over the repository, with its own store, and zero authority** — a deliberate one-way dependency: the service consumes `repo.list()` and read-only session opens; the repository knows nothing about search and exposes no search methods. Indexing is pull-based with durable per-session cursors (`sync()` enumerates and catches up, `notify()` is just a debounced freshness hint that never carries content, a lost poke is caught by the next sweep), rows are indexed idempotently per (sessionId, entryId), and a crash mid-batch re-indexes into the same state. "The index is a rebuildable projection with zero authority: indexing failures never affect the harness or commits." The reference implementation is one standalone SQLite database with an FTS5 table over (session_id, entry_id, text) plus a cursor table, working unchanged over JSONL session files. This landed on main as the search refactor [`b75be04d9`](https://github.com/earendil-works/pi/commit/b75be04d9) (#7797) with its own doc `search.md`. The open question is metadata filtering (how a repo-specific filter like coding-agent's `cwd` reaches the generic index), with four candidate designs listed and left to "the people who will fight over it."

## The j4 branch in detail

`harness-v2/j4` carries the v2 doc plus one compat slice, 5 files, ~830 lines: [`packages/agent/src/harness/session/jsonl/v3.ts`](https://github.com/earendil-works/pi/blob/harness-v2%2Fj4/packages/agent/src/harness/session/jsonl/v3.ts) (186 lines), tweaks to `jsonl/storage.ts` and `jsonl/errors.ts`, a hook in `session/state.ts`, and a 589-line test file `jsonl-v3.test.ts`. What the code does:

- Detects old coding-agent v3 files by their header line (`type: "session"`, `version: 3`) and normalizes them into the new harness's session mutation/entry types: `custom_message` becomes a custom agent message, `label` and `session_info` become facts, legacy `model_change` / `thinking_level_change` / `active_tools_change` nodes disappear (children reparented to the nearest retained ancestor, the `main` leaf resolved through discarded nodes), old compactions materialize their `firstKeptEntryId` range, timestamps convert from ISO to Unix milliseconds, unresolved `parentSession` paths are preserved as `legacyParentSessionPath`.
- Strict decode errors throughout — `JsonlDecodeError` with `syntax` vs `schema` kinds, a `decodeResult` wrapper that converts throws into tagged errors, and null-tolerant field readers — the theme being: an old file either normalizes cleanly or fails with a precise error, never silently drops.
- There is a `TODO(J6)` in the code — the j-slices are numbered work streams and the compat work is expected to continue in a later slice.
- The branch's own doc commit history shows the v2 doc evolving through "split harness v2 into effects and generator variants" (2026-08-02) to "finalize harness v2 on the effects variant" (2026-08-03) — a design decision worth noting: two candidate mechanism styles were written up and one was chosen.

The catch: the branch's normalization targets the v2 session types (records/facts), and main's v3 spec says slice 1 deletes `packages/agent/src/harness/**` outright and rebuilds, with the format-3 compat rules restated in Appendix B (notably adding id re-minting: legacy ids become UUIDv7s with the legacy entry's timestamp as prefix, and every reference the format knows — parent chains, main's leaf, label keys, `fromId`, usage `entryId` — is remapped). So j4 is a clean, well-tested piece of work whose *rules* survive into the final spec but whose *code* will not survive the rewrite. The branch has been quiet since 2026-08-07, right when the design sprint began — consistent with the team pausing feature slices while the spec churned.

## The audit process (worth stealing)

The way the spec was stabilized is a process worth copying. After the v3 draft was complete, the team ran two "cold read" audit rounds with an AI reviewer (the findings file says "second cold read, gpt-5.6-sol"): a fresh model reads the spec end to end and files findings by severity, each finding a concrete contradiction or unimplementable claim, each fixed in the document itself, and the findings file deleted when empty. The recorded second round — [`harness-v3-audit-findings.md` at `cf5f35216`](https://github.com/earendil-works/pi/blob/cf5f35216/packages/agent/docs/harness-v3-audit-findings.md) — lists 17 findings, including three P0s: retention contradicting the "no third place" storage model; a settlement kernel that "cannot perform its claimed settlement" because it stored only untyped id arrays; and retention preflight dropping entries that open-state validation requires. The fixes are visible in the final spec: retention was demoted from a live feature to an informative "future Postgres" part, invariant 19 was re-scoped to the committing transaction, and the settlement state carries discriminated records. Ten findings from the first round were already fixed in [`8431bfbea`](https://github.com/earendil-works/pi/commit/8431bfbea). This is a spec-first red-team loop, and it visibly changed the design.

## What I think is happening here

**Pi is being re-platformed from a CLI app into a durable runtime.** The interactive coding agent was built session-by-session over years; the harness is the consolidation of everything the team learned about sessions, compaction, subagents, and crash handling into one well-specified engine — and the repo layout shows the platform shape it enables: `packages/server` (experimental server package), `packages/client` (transport-neutral client over framed CBOR), `packages/protocol`, and `packages/coding-agent/src/server/create-harness.ts` already wiring the real tools into an AgentHarness for a server mode. The doc's own examples — Slack channels and email threads as sessions with parallel lanes — name the product direction: pi running as a service hosting many conversations, each with threads, subagents, and forks, surviving restarts mid-tool. The interactive TUI is being left alone for now ("migrating coding-agent to AgentHarness is out of scope" — compatibility means the new store reads old files), which is the pragmatic call: don't destabilize the shipped app while the platform underneath is rebuilt.

**Why durability gets this much design attention.** The hard requirement the whole design exists to satisfy is: an accepted prompt is a promise that survives process death, and nothing external runs twice. The effect sandwich (intent commit → effect → settlement commit), the replay policy (`safe` vs `never`) for tools, the fenced writer lease, and the program-counter register are all one answer: make the uncertain window as small as one provider request or one tool call, and make the state after any crash explicit rather than inferred. The v2→v3 change is the interesting intellectual move: v2's operation logs are a *journal you must reduce* — recovery replays records to reconstruct position, and a buggy reducer corrupts recovery. v3's registers are *the state itself* — recovery is five point-reads, "no reducer exists to have a bug." The cost is the total-state rewrite after every step and the burden it places on schema evolution (total migrations for every reachable old state), and Part 7 is the argument that this burden is bounded because the mutable surface is small and open operations are usually zero. It is a coherent, well-argued trade — durability bought by making orchestration ephemeral and the conversation boring.

**Why the churn is a feature, not a bug.** The code landed in May-August, then the spec was rewritten twice in three days, then the spec told the implementers to delete the code. If you judge by shipped diff, that looks wasteful; judged as engineering process, it is the opposite — the team wrote the implementation as a probe, extracted the design lessons, and is now spending the design budget where it is cheap (documents, cold-read audits) before spending implementation budget where it is expensive (16 slices, two tracks). The build order even encodes the lesson: slice 1 is "delete the old code, land the types," and every slice must stop and escalate if implementation exposes a design contradiction. This is exactly the red-green discipline applied to architecture, with an AI reviewer as the second set of eyes.

**The resonance with our own principles is real.** The v3 invariants read like our notes folder principles in another dialect: entries write-once and append-only ("facts are written once when they happen and never rewritten"); every index is a disposable cache ("the search index is a rebuildable projection with zero authority"); layers stay ignorant of the one above them (search depends on the repository one way; storage knows nothing about execution); the simplest durable thing (one file per session) beats the general system. The one deliberate double-write (queued payloads serialized into a `pending.entry` register and then into an entry) is justified with the same cost/benefit framing we use: only the queued path pays it, and in exchange every queue item has one id and one owner.

**What it means for us.** The dispatcher runs pi as a subprocess runner today, and botassembly's runtime (`bot`) has its own sealed-record model. The harness is the upstream answer to problems we have already met or will meet: a worker that dies mid-tool and must resume without re-running a side effect; several threads of work over one conversation; a subagent whose child session must be discoverable after a crash; cost accounting that survives restarts (the usage ledger); and testability by driving the loop step-by-step (our dispatcher's own "sealed record" instinct). The deferred-request machinery (persisted provider handles, pay-once) is also directly relevant to subscription-quota agents. None of this changes what we run today — interactive pi 0.84.2 still uses the legacy runtime — but the direction of the platform is now legible, and when the harness matures it will be the natural substrate for dispatcher workers, dashboards, and botassembly rather than something separate from them.

## Risks and open threads

- The j4 compat slice is built against v2 types that the v3 plan deletes; its rules survive (Appendix B) but its code will be rewritten in slice S1. If you were hoping to use that branch for anything, don't build on it.
- The build plan is honest that the interactive coding agent is not migrating; two runtimes (legacy coding-agent sessions and the harness) will coexist for a long time, with the compat bridge (read old v3 files, normalize on load, convert on first write) as the only contract between them.
- The spec's open questions are small but telling: overflow detection remains heuristic; repairing a missing model identity captured inside an open operation has no API; pending-payload write amplification is unmeasured.
- The audit process caught real P0s in the v3 draft, which means the spec can still surprise; the build order's "stop and send it for review" rule is the designed safety valve for that.
- Nothing in the branch or the spec changes the shipped interactive pi soon. The server package is still labeled experimental; the harness API was only promoted out of the experimental module in early August.

## Business context — why the trust properties exist

The compliance vocabulary in the spec (erasure, retention, audit, single writer) is not incidental; the repo shows the business the harness is being built for. Earendil already runs a live gateway product, **Radius** — `DEFAULT_RADIUS_GATEWAY = "https://radius.pi.dev"` in [`packages/ai/src/providers/radius-config.ts`](https://github.com/earendil-works/pi/blob/main/packages/ai/src/providers/radius-config.ts), with a live OAuth discovery endpoint whose issuer is `https://radius.earendil.com` (device-code flow, PKCE, client id `pi-gateway`). Radius speaks pi's own wire protocol, `pi-messages` ([`packages/ai/src/api/pi-messages.ts`](https://github.com/earendil-works/pi/blob/main/packages/ai/src/api/pi-messages.ts)): one POST of `{ model, context, options }` to `/messages`, an SSE stream back — and, critically, a **server-side message rewrite policy structure** (`PiMessagesRewriteImpact`: `policyId`, `policyVersion`, `tokenCountChange`, `systemPromptChanged`). A gateway that rewrites messages before they reach a model is a governance choke point: redaction, mandatory system prompts, routing, token accounting. Enterprises can declare their own Radius gateways in models.json (`oauth: "radius"`) — the self-hosted edition pattern.

Alongside it: **Gondolin**, their own micro-VM sandbox ([`github.com/earendil-works/gondolin`](https://github.com/earendil-works/gondolin), npm `@earendil-works/gondolin`), the security doc's blessed isolation answer for routing built-in tools into a VM ([`packages/coding-agent/docs/containerization.md`](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/containerization.md)); **PiServer** ([`packages/server/README.md`](https://github.com/earendil-works/pi/blob/main/packages/server/README.md)) — a session server core with pluggable transports and per-listener auth over the CBOR wire protocol, the open-sourced shape of the "serving layer" the harness spec keeps deferring to; hosted session sharing through Radius ("only share via radius if logged in"); and OAuth subscription logins brokered through pi for existing subscriptions. Read together: pi (the agent) is free; the money is in the choke points between the agent and everything it touches — the gateway (policy, identity, routing, spend), the sandbox (isolation), and the durable serving layer (audit, erasure, retention). The harness is the audit-grade substrate that makes the enterprise story true: the usage ledger is the audit trail, the precise rewrite is "compliance-grade erasure" as the sole sanctioned deletion, Part 6's partitioned Postgres is retention policy, and the fenced single writer plus corruption invariants are tamper evidence. The companion note `pi-harnessv2-questions.md` carries the questions worth asking the team; this section is the evidence behind them.

## Botassembly callouts — using pi as the runtime foundation

Botassembly is not waiting for the harness; it is already built on it. `bot/src/machinery.ts` in the botassembly repo imports `AgentHarness`, `JsonlSessionStorage`, and `Session` from `@earendil-works/pi-agent-core`; `bot/src/pi-tap.ts` taps `AgentHarnessEvent` into the record; `bot/src/turns.ts` wraps every prompt in a guard that aborts the harness if the provider never settles. The ADRs in `~/workspace/repos/botassembly/sdlc/planning/adr/` record the posture: agent-core not coding-agent (0002), exact-pin and bundle with zero deep imports (0003), one process per run (0005), **pi's session file is the session artifact** (0006), retry doctrine with no runtime retry machinery (0009), and ranked upstream engagement (0011). Against that posture, the v3 work raises specific concerns.

**The foundation is scheduled for demolition.** The v3 build order slice 1 says "Delete `packages/agent/src/harness/**` and its tests outright" and rebuild on a new type surface. Everything bot touches — `AgentHarness`, `JsonlSessionStorage`, the event catalog, the session types — is inside that blast radius. Bot's pin-and-bundle doctrine (0003) protects against today's weekly breaking releases, but it does not protect against the surface bot is pinned to being deleted upstream; a pin of a deleted API is a dead end, not a shield.

**The semantics bot rests on are the provisional ones.** ADR 0011's first ranked ask is to stabilize harness prompt/idle semantics — "prompt() resolves ⇔ agent went quiet" — because the gating model (ADR 0007) rests on it. v3 redefines the same ground: acceptance, queues, `LaneBusy`, checkpoints, abort reconciliation. Bot's prompt guard, abandoned-prompt bookkeeping, and ghost-record logic in `turns.ts` are hand-rolled compensations for v2 semantics; v3 changes the rules they compensate against.

**The event catalog is bot's capture surface.** ADR 0006 says per-turn facts come from the live event stream (ADR 0008), not from re-parsing session files. v3 Part 5 reworks events — ordering, filtering, nesting — and the spec's own conformance tiers assert exact event order. Bot's `pi-tap.ts` is a schema over that stream; a subtle semantic shift during a pin upgrade would corrupt the record's honesty guarantee (ADR 0020) quietly, and only bot's qualification runs would catch it.

**The session-file bet rides on format stability.** ADR 0006 makes pi's JSONL the session artifact and renders `bot session` against the pinned schema. The format has already churned (coding-agent v3, then harness format 4, with v3's plan saying the current format-4 code is "unfinished" and "replaced in place" with no migration). The bet survives because the reader is pinned alongside (0003) — but each deliberate upgrade adds another format generation bot must render, and the record-referenced layout (`stages/<stage>/<repeat>/session.jsonl`) must keep working across generations.

**Resume-vs-fail is an unresolved collision.** The harness's core promise is that an accepted operation resumes after a crash; bot's doctrine (0009) is that a surviving provider failure is recorded, not classified — stage fails with cause `fault`, exit 2 — and the dispatcher's contract is exit codes with external retry. Where an in-engine resume ends and a bot fault begins is unspecified upstream, and the answer lands exactly in bot's adapter.

**Embedder ergonomics are a second-class concern upstream.** ADR 0011 ask 6 — move `ModelRuntime`/`AuthStorage` out of the interactive product so embedders don't reimplement a locking credential store — is still open. The v3 spec keeps auth resolution inside the harness's Models dispatch, but the credential layer's home is unchanged. Bot embeds today by accepting interactive-product coupling; the v3 rewrite is the moment that coupling either gets fixed or gets set in stone.

## Opportunities for botassembly

**Several ADR 0011 asks are already answered by the v3 spec.** The ranked list's truncated-turn repair — "a sanctioned synthesize-cancelled-tool-results and continue" — is exactly v3's synthetic settlement after crash or abort, with replay policy (`safe` vs `never`) as the designed answer to which tools may re-run. The spec's abort reconciliation and failure drain are engine-native versions of bot's abandoned-prompt and ghost-record machinery. The window between spec and slices is the moment to file the remaining asks (resume-vs-fail semantics, event ordering guarantees, conformance-suite export) — bot is one of very few in-process embedders, and the team demonstrably answers (ask 4 landed as design).

**The conformance suite and drive modes could absorb bot's testing machinery.** Bot's scripted-model and faux-provider needs (ADR 0011 ask 2's testing helpers) map directly onto manual drive plus the instrumented-storage decorator: byte-identical durable state between automatic and manual drive is the oracle bot's evals folder wants for replaying a recorded run.

**The usage ledger could feed the record's cost facts.** Today the record collects usage from tapped events (ADR 0008). The v3 ledger is append-only, session-scoped, and survives everything — a cleaner source for the cost line in bot's sealed record, with adjustment rows for imports and forks starting at zero.

**Lanes and forks are a possible successor to subflow processes.** `bot/src/subflow-runtime.ts` runs child flows as nested runs; v3 lanes (parallel named cursors over shared history, one writer) or forks (entries-only copies with deterministic child ids and `parentSessionId` linkage) are the engine-native shapes for subflows — worth evaluating when the runtime track lands, not before.

**Deferred requests fit quota-limited work.** Bot runs subscription models; the v3 `deferred` stream option with persisted provider handles is pay-once machinery for background-capable providers, when any actually ship it.

**Regulated-work readiness is inherited.** If the dispatcher ever takes work that needs audit, erasure, or retention (the clinical domain is the target buyer for exactly these features), riding the harness inherits the compliance posture described in the business-context section: ledger as audit trail, precise rewrite as sanctioned deletion, retention as designed policy — rather than bot having to invent each of them.

## Public positioning — the dev-notes read (2026-08-22)

Pi's public dev notes (circulating as a widely-shared tweet thread) frame the harness work as a direct attack on the other harnesses' durability, and the framing matches what the repo shows. The claims, with grounding status:

- **The competition moved from features to durability.** The differentiator is no longer tool count or demo flash but "does an agent that runs for 50 hours still know what it's been doing" — a state-management question, which is precisely the one harness v3 answers.
- **Prune + spill vs. lossy pruning (the DSH roast).** DeepSeek Harness prunes long tool results head+tail, permanently deleting the middle — if the real error sat at character 12,000 of a 30k log, no later cleverness recovers it. Pi's answer keeps a short snippet in context but spills the full output to disk with a pointer (path + offset); the model greps/reads it back on demand. Claimed results over 19 real sessions (GLM-5.3, DeepSeek V4 Flash): 26–35% context reduction, 72–88% uncached-prefill reduction, nothing permanently lost. **Grounding: as of tip `c49906ec7` no spill code or PR exists in the repo — the numbers are claims about work in flight, not verified.** The design argument holds regardless: the expensive tokens are the uncached ones, and moving content to disk instead of the void preserves recoverability — the same trade our own records doctrine makes.
- **Model-harness binding (the Claude Code observation).** Newer Claude models on third-party harnesses emit tool parameters that don't exist there — `requireUnique`, `matchCase`, `oldText2`, Claude Code's edit-tool vocabulary leaking into other harnesses' schemas. Hypothesis: post-training overfit to the vendor's own harness. Implication: model and harness are fusing into single products (Claude+Claude Code, DeepSeek+DSH, GPT+Codex), so "which model is best" becomes unanswerable in isolation — only "which model+harness pair."
- **The transactional harness, stated publicly almost exactly as the spec has it**: intent write before a tool runs, settlement write after, recovery reads saved state instead of guessing; lanes hold their own positions; context compresses, raw execution history never gets destroyed.
- **Boundaries over plugins.** Against the "everything is a plugin" fashion (DSH's Cordis named), pi draws hard lines — conversation, runtime state, UI, extension; some things persist, some only observe. The closing metaphor is the thesis: the harness as the OS of the AI era — process management, memory hierarchy, crash recovery, scheduling wearing an agent costume.

## Evidence in our own session data — and an accidental validation

Two findings from `experiments/166-pi-log` (the session-observation CLI built 2026-08-22 over seven months of local session history) bear directly on the dev-notes claims:

- **The model-harness binding is visible in our logs.** Across 159k messages and 56k tool calls: tools named `<tool_call>bash` (a model emitting raw markup instead of a proper call), `list_directory` (not a pi tool — another harness's vocabulary), and blank-named tools. These are exactly the failure species the binding hypothesis predicts: models guessing harness schemas they were trained on elsewhere. Bot runs Claude/Codex models through pi — a third-party harness — on subscription providers, so this risk lands on us directly. The pin doctrine's qualification runs are the detection; there is no cure on our side, which makes it a standing risk rather than a fixable bug.
- **Pi-log independently rebuilt prune+spill.** Raw tool outputs are deliberately never indexed; the index holds pointers (file path + line) and `search`/`show` dereference into the original file on demand. Same shape, reached from the same cost/benefit instinct, in a 200-line indexer — evidence the pattern is the natural one, not an exotic choice. Pi-log's other convergences with the v3 search service (disposable index with zero authority, FTS5 over SQLite, watermark-based incremental sync, never-index-content rules) suggest the instincts scale in both directions.

## What the positioning means for botassembly strategy

The dev-notes thesis is our doctrine argued at the harness level. Bot's sealed record *is* "raw execution history stays intact; summaries are projections" — ADR 0020 and ADR 0006 made the same bets the spec now encodes, and the boundaries-over-plugins stance is the dispatcher's own layering rule (each layer ignorant of the one above) applied to a single process. The inheritance path stays as the opportunities section describes: when the v3 runtime track lands, the hand-rolled crash compensations in `turns.ts` (prompt guards, abandoned-prompt bookkeeping, ghost records) are deletable in favor of engine-native synthetic settlement, abort reconciliation, and durable recovery. The binding risk is the genuinely new item: it adds a third standing risk alongside pin-stranding and event-catalog drift, and it degrades quality rather than breaking code — the worst kind, because it shows up as subtly worse runs rather than as errors. And the resume-vs-fail collision remains the single most important upstream question: the tweet's "the system needs to know whether that tool actually ran" is exactly bot's adapter seam, and the spec-to-slices window — while the design is still a document and the team is demonstrably answering embedder asks (ask 4 landed; truncated-turn repair landed as synthetic settlement) — is the cheapest influence bot will ever get.

## SWOT — the harness as botassembly's foundation

**Strengths** (properties of the harness itself)

- Recovery-as-read plus synthetic settlement removes a whole class of hand-rolled crash scaffolding from bot (abandoned prompts, ghost records, prompt guards in `turns.ts`), and the replay policy answers the rerun-safely question by design.
- The three-stores model (write-once entries, mutable registers, append-only ledger) matches bot's own record philosophy — honest records, never blocking progress (ADR 0020) — and the ledger is a better cost source than tapped events.
- Deterministic drive modes and the backend conformance suite are test infrastructure bot needs anyway (ADR 0011 ask 2); automatic-vs-manual byte-identical state is the eval oracle.
- Single-writer enforcement with a fenced lease matches and enforces bot's one-process-per-run posture (ADR 0005).
- The spec's discipline — enumerated invariants, race catalog, cold-read audits — gives bot a reviewable contract instead of reverse-engineered behavior.
- The durable surface is stable by design (entries and ledger read-compatible forever, orchestration ephemeral), which is exactly the property ADR 0006's session-file bet needs.

**Weaknesses** (risks in choosing it as a foundation today)

- The v2 surface bot depends on is marked for deletion upstream; the pin protects against breakage but not against obsolescence.
- v3 is a spec, not code — the runtime track is twelve sequential slices; until it lands, bot stays on v2 with no upstream fix path for harness bugs.
- The provisional prompt/idle semantics bot's gating model rests on (ADR 0011 ask 1) are still provisional in v2 and get redefined in v3.
- The event catalog rework threatens bot's capture path; record honesty depends on event semantics that v3 will change.
- Embedder ergonomics remain second-class (auth/model-runtime in the interactive product, ADR 0011 ask 6).
- JSONL format churn means ADR 0006's bet accumulates format generations bot must render and qualify.

**Opportunities** (external openings for the botassembly team)

- Shape the v3 API during the spec-to-slices window: file the remaining ADR 0011 asks now, while the design is still a document and the team is visibly answering embedder feedback.
- Replace bot's crash-compensation machinery with engine-native abort, reconciliation, and synthetic settlement when the runtime track lands.
- Evaluate lanes/forks as the successor to subflow processes; evaluate the ledger as the record's cost source.
- Inherit compliance posture (audit, erasure, retention) for future regulated dispatcher work.
- Use deferred requests for quota-limited subscription models if providers ship them.
- Borrow the conformance suite and drive modes as the evals oracle.

**Threats** (external forces working against bot)

- The rewrite could land with a surface shaped by Earendil's server products, not embedders — bot becomes a second-class consumer of an API designed for the serving layer.
- Model-harness binding: if leading models keep tightening to their vendors' harnesses (the dev-notes evidence), any model run through pi — and thus through bot — degrades relative to first-party pairings. Our own session logs already show the failure species (`<tool_call>bash`, foreign tool names like `list_directory`). Qualification runs detect it; nothing cures it on our side.
- Pin-stranding: v3 landing turns the v2 pin into a dead end, and v2 bugs (the transport-retry bug is the precedent) stay unfixed while the only upgrade path is a rewrite.
- Business pivot: if the harness becomes the substrate of the hosted product, open-source embedder support could drop in priority, or gateway-required features could create soft lock-in to Radius.
- Semantic drift on upgrade: subtle event or ordering changes could quietly corrupt record honesty, caught only by bot's qualification runs.
- Upstream cadence outruns deliberate upgrading: several releases a week against branch-qualify-land means the qualification window may exceed a pin's shelf life.
- The resume-vs-fail collision: the harness's accepted-operation-is-a-promise against bot's fault-and-exit doctrine (0009) and the dispatcher's exit-code contract could turn bot's adapter seam into a fight with the engine.
- Spec churn precedent: v2 to v3 happened in three days; another redesign could strand bot's accumulated glue the same way the current one strands the v2 code.
