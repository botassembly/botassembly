# Nothing outside the agent decides done, loop, or choose

Observed 2026-09-18 at commit `f78074e` on the Linux box.

Every decision about moving on belongs to an agent today. `CHOOSE.md` is answered by an agent with the `select` tool, and the specification closes the door on anything else: "There is no other chooser" (`specification/elements/choose.md:58`). The settled vocabulary says the same: "There is no deterministic chooser", ruled with ticket 0022 (`sdlc/planning/vocabulary.md:27-29`). A loop's last stage is asked whether to go again and answers with a control tool (`specification/elements/loop.md:48-65`). A descend is an agent's call too: a stage inside the flow decides how its input divides and calls the flow on the pieces (`specification/elements/descend.md:37-49`). A stage's checklist is marked by the agent that did the work, and the runtime declines to judge the evidence text: "its quality is for the checklist author to demand, not the runtime to judge" (`specification/elements/checklist.md:50-51`). The gate is the one check that "judges the work rather than its form" (`specification/elements/gate.md:8-9`), and a gate sees only `$INPUT` and `$OUTPUT`.

Ian reopened this on 2026-09-18. Asked whether he would reopen "no other chooser", he said: "Yeah, definitely." His reasoning: a decision needs context. The agent that holds the context is the one that just finished, so it grades itself. A fresh agent would have to load all of that context again. A small outside decider avoids both costs if the finished stage boils its context down to a manifest. He drew a line between two things the specification treats as one. A checklist reminds the agent and records that the agent says it did a thing. Success criteria define done for a stage, and something outside the agent decides whether they are met. His words: "Checklists are kind of like grading yourself, whereas this is more about having an external system that's focused on deciding when to say you're done." He also said not every stage needs success criteria.

His model has three parts. A stage may declare success criteria. The agent hands over a manifest with receipts: what it did and the results. A decider reads the criteria, the manifest, and possibly script output, and says whether the stage met its goals. The same decider could answer a loop, a choose, or a descend.

Evidence from an experiment outside this repository, run the same day. A fast classifier model that answers yes/no questions with a probability (TypeSafe's Jev) served as a gate through a plain criteria file and a two-line gate script, with no change to Bot. It judged 120 accepted stage outputs drawn from sealed run records of public repositories. Where the stage input was a real document, the gate caught every request that code had swapped for another run's, and it wrongly rejected 1.7% of accepted work at a pass mark of 0.60. Where the stage input was only a ticket path, it caught about a quarter of swapped requests at that mark. The finding is that an outside decider judges only what it is shown. That is the case for a manifest. The record already keeps each checklist item's evidence text, and real evidence scored well above evidence swapped in from another run, so the receipts are partly on disk already.

Constraints any answer has to respect. Bot calls no provider except through Pi (ADR 0001), and this runtime is public, so a hosted classifier cannot live inside Bot. A decider therefore has the shape of a gate: a program in any language, called with slots, answering by exit code and printed text. `bot check` promises that a run's graph is known before it starts. A program that picks among alternatives already listed in `CHOOSE.md` keeps that promise. A manifest written by the agent is a self-report, so a decider that reads only the manifest can be talked into a pass. Receipts the runtime observed itself, such as commands run and check results, do not have that weakness.

Smallest outcome that closes it: a ruling on three questions, and the specification text that follows from it. First, whether a stage may declare success criteria apart from its checklist, and where they live. Second, what the manifest is and who writes it: the agent's receipts, the runtime's own account from the record, or both handed to the decider under separate labels. Third, whether `CHOOSE.md` and a loop's tail may name a program as the decider, with the agent asked only when the program declines. Descend is a weaker fit. How an input divides is writing, and a decider does not write. Only the yes/no of whether to split at all is a decider's question.
